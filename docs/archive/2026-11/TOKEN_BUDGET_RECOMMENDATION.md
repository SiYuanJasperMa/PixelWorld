# PixelWorld 外部 token 预算建议

日期：2026-11-08。仅统计与建议，没有启用截断、改变已有run或启动新模型调用。证据见 [分析结果](../runs/token_budget_review_20261108/report.json) 与 [逐run表](../runs/token_budget_review_20261108/per_run.csv)。

后续用户选择50k累计output阈值，外部控制见 [TOKEN_RUNTIME_BUDGET.md](TOKEN_RUNTIME_BUDGET.md)。15分钟时间预算原型已撤回。本文的32k建议保留为此前的数据分析依据。

## 用token作主预算，时间作运行保障

主预算定义为每段视频任务累计API assistant output tokens，包含推理、代码、工具参数、检查文字。若output已含reasoning，不重复相加；未披露的推理用量标记unknown。input与缓存tokens另行记录，用于分析成本和重复上下文开销。

API latency存在排队、网络和部署波动。固定墙钟预算会把这些因素混入生成能力评价：同一生成量，慢服务可能提前耗尽时间。固定token预算限制生成量，对此更稳定，但同样不是等FLOPs或等美元。不同tokenizer、推理架构、输入长度及缓存策略都需要披露。

时间限制保留为API/工具卡死的运行保障；设置较宽松并记录触发原因，不与token耗尽混为同一失败原因。必须报告超时数量及其影响，不默默剔除。主文报告质量与token预算、实际成本的关系；墙钟时间与服务波动作为配套结果或附录。

## 建议值

对当前主测GPT-6.1-Sol、GPT-5.6-Sol，建议 **32,000累计output tokens/视频任务**。这个值是保守地留足首次生成、调试与自主修订余量，同时限制额外长尾。

预算数字只在外部harness配置中出现，不写进agent任务。建议任务中仅加：

> 避免没有明确改进目标的反复检查或重复执行。

仍允许自主修订，不固定review次数、不要求首次有效保存即停止。Token预算限制消耗，不能严格保证只产生1–2个候选。

多benchmark smoke：GPT-5.6的11段完整output为4,380–12,196；GPT-6.1的5段为7,715–20,599，全部≤32k。它们是少量artifact smoke，不足以证明新benchmark全量覆盖率。

## 首次候选与后续工作

旧v1采用ephemeral CLI，只保留终端会话总usage，没有首次保存的逐请求token水位。不能用“总tokens×首次耗时占比”估计首次token消耗。

八条新fulltrace-v2诊断run有逐请求`token_usage_record`。去重后求和与每条终端总usage完全相等。在首次候选快照时间点，已上报累计output为4,808–12,410。0035 Text的前两次不同RGB快照分别为10,009、11,749；它在不到18k内产生4个不同RGB候选，说明token预算与候选次数不是一回事。

这些是观察器快照时间对应的API累计用量，不是独立标记的渲染完成时间。四个case按此前结果选取，且采用新v2提示，不能外推全量首次候选P95。终端总量≤预算的既有完整run，为其首次候选在预算内提供保守总量依据；总量超过预算的run，其首次候选是否在预算内仍未知。

## 跨模型边界

现有DeepSeek-V4-Pro Text的197个完成case，总output中位53,648；Seed Text的63个完成case中位103,648，Vision-Agent的52个完成case中位153,040。32k覆盖其完整运行分别仅14/197、3/63、0/52。它们也缺首次候选token水位，因此不能证明同预算能让这些模型大多数产出首版。

若采用跨模型共同32k预算，预算不足可以作为结果，但不能声称保证所有模型的首次提交覆盖率。若要求Seed/DeepSeek也大多数完成一次生成，需要补充完整trace的首次用量后再选择共同预算。不用不同模型的完整run中位数直接分配不同上限，再声称同预算公平比较。

## 外部切断规则

- 预算单位是一次生成一段视频的任务；同任务重开会话时累计消耗不清零。WBench等多轮任务每次视频生成另有预算，同时保留episode总成本。
- 外部记录逐请求累计usage及候选保存事件。达到预算后停止新模型请求，冻结预算内最后一个完整、格式正确的RGB候选；按时间选择，不按评测分挑选。
- 没有有效候选则记budget-exhausted。允许机械验证和导出，不再调用模型修复；不覆盖旧结果。
- 请求结束后才发现超预算并杀CLI，是软上限，必须记录overshoot。严格上限需要在请求边界按剩余预算限制单请求输出，并阻止预算耗尽后的请求；只监控terminal总usage无法实现。
- 新fulltrace已能在请求完成后提供累计usage，但请求限额、外部终止及候选冻结仍需实现与smoke验证。当前不宣称硬预算已生效。
- 新尺寸/FPS或新benchmark需要先smoke，不由现有低分辨率数据保证所有规格均能完成。

## Solve Vision with Code 的参考价值

该文在VBVR-Pro的100任务×5实例上使用官方规则评分，比较3个闭源coding agent、24个开放模型和公开的视频模型baseline。每题一次独立agent会话，内部可多次执行/修改；1800秒外部墙钟上限，无重开重试或best-of-N。

分析顺序为全量成绩、ID/OOD与类别、工具/token/耗时/交付效率，再区分交付失败与内容失败，读实际程序及评分器解释成败，展示成功程序并界定结论范围。它没有系统评估逐版修订收益，也没有使用本文建议的32k token上限。其效率比较存在CLI、输入图像访问方式等差异，应视为运行系统的比较，不直接当成相同模型内部组件的因果实验。
